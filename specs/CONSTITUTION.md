# 项目宪法 (Constitution)

> 本文件是工作流的最高法则。任何 Skill 开始执行前，必须先读本文件并遵守。
> 与旧版 `GUARDRAILS.md` / `PROJECT-CONTEXT.md` 的关系：本文件取代两者。老项目中若存在旧文件，读取但不冲突执行，以本文件为准。

---

## 一、上下文加载协议

开始任何工作前，**按需**加载上下文。禁止全量读取 `specs/` 目录——token 是稀缺资源。

**每次必读：**
1. 本文件（specs/CONSTITUTION.md）
2. `specs/TOOLCHAIN.md`（若存在）——本项目的测试/验证工具链配置

**项目级文档，按任务相关性选读：**
- 做产品/需求相关工作 → `specs/产品概述.md`
- 写代码/做技术设计 → `specs/技术栈.md`、`specs/开发规范.md`、`specs/项目结构.md`

**功能级工作，只读当前功能的文档：**
- 正典三件套：`specs/features/{功能名}/需求.md`、`技术方案.md`、`任务规划.md`
- 开发日志：`specs/features/{功能名}/开发日志.md`
- 进行中变更：`specs/changes/{功能名}/CR-{编号}-{中文slug}/` 下的相关变更文件夹

其他功能的文档**不读**，除非做跨功能影响分析（此时只 grep 相关引用，不全文阅读）。

**旧结构兼容：** 若功能文档是旧版单文件（`specs/features/{功能名}.md` 及 `_技术方案.md` 等），按旧路径读取，行为一致。

**旧结构写入（日志类文件）：** 读取跟着旧路径，**写入跟着项目现状走**——该功能目录里已经存在日志文件（`开发日志.md`、`_journal.md`，或其它历史命名），就追加到那一个，**不要新建第二份**；只有项目里完全没有日志文件时，才按下面的命名约定创建。追加时沿用文件里已有的条目风格，不要强行改写历史条目的格式。

**机制文件缺失协议（老项目接入）：** 若项目没有 `specs/CONSTITUTION.md`，说明它还没接入 SpecForgeX。所有 Skill 统一按下面三步处理，不得各自发挥（有的自动建、有的问一句、有的直接跳过）：

1. 询问用户是否初始化 `specs/CONSTITUTION.md` 与 `specs/TOOLCHAIN.md`——这是唯一允许在需求对话前创建的文件。
2. 同意后，从技能包 `project-requirements-clarification/assets/` 复制 `constitution-template.md` / `toolchain-template.md` 生成这两个文件；该 Skill 未安装时用任一已安装 Skill 的同名副本；都没有则请用户手动提供，**不凭记忆重写**。
3. 用户拒绝则继续工作，但在本次产出文档中标注"未接入 SpecForgeX 机制文件"。

TOOLCHAIN 此时保留 `{{占位}}`，由 project-initialization 或首次需要执行验证时引导填写。

**并发约定：** 文档是跨会话的唯一共享状态，而多数工具对文档是整文件重写。同一功能同一时间只开一个执行窗口（feature-implementation / 变更任务执行）；确需并行推进多个功能时，各自改各自的功能目录，公共文档（本文件、TOOLCHAIN、项目级文档）的修改集中在其中一个窗口完成，否则两个窗口会互相覆盖对方的写入。**编号也按功能分区**——AC / Task / CR 都只在本功能的目录内自增取号，因此不同功能并行开发不会撞号（跨功能引用一律带功能名限定）。

## 二、项目原则

1. **文档先于代码**——所有决策落到文档上再动手，文档是跨会话的唯一记忆。
2. **AC 贯穿全链路**——每条验收标准（AC）从需求、技术方案、任务到测试全程可追溯，任何一环断裂都要暴露。
3. **TDD 按任务分类执行**——纯逻辑严格 TDD；UI 任务用浏览器验收兜底；schema 变更用迁移+查询验证。不表演 TDD。
4. **最小改动**——只改必须改的，不顺手重构无关代码，不另起一套已有实现。
5. **复用优先**——先看项目里已有什么可复用，再决定要不要新建。
6. **代码与文档同步**——实现中发现与文档不一致，当场修正文档，不允许漂移过夜。
7. **上游文档变更必须传播**——修改任一项目级文档（技术栈 / 项目结构 / 开发规范 / TOOLCHAIN）时，同一次工作里必须列出受影响的下游文档清单，逐项同步，或明确标注"待同步 + 原因"；功能级文档的连带调整小的就地改、大的走 feature-evolution。只改一处就收工是不完整的交付。

## 三、阶段边界守卫

每个 Skill 只做职责内的事：需求阶段不写代码，设计阶段不做实现，规划阶段不执行，编码阶段不改变需求的范围（AC）。

**实现中发现文档与实际不一致时，按性质分两种，不要一刀切：**

| 性质 | 例子 | 处理 |
|---|---|---|
| **事实性偏差** | 字段名、路径、文案、流程细节写错；文档漏了一次明显必要的状态 | 当场就地修正文档并追加一条开发日志——这属于"代码与文档同步"（原则六），不算改需求 |
| **AC 行为变更** | 新增/修改/删除一条验收标准，或改变用户可见的行为 | 不在实现阶段就地改，走 feature-evolution 开 CR；用户要求临时绕过时先确认并记录，再按越级处理 |

用户在本阶段索要下一阶段的产出时，不道歉、不说教，直接说明：*"这属于 {下一阶段} 的事，当前先把 {当前阶段的产出} 确认下来，避免返工。"* 然后引导回当前职责。

**用户显式越级出口：** 当用户明确表示"我知道风险，直接做"（或同等明确的表述）时，放行执行，不再阻拦；但必须追加一条越级记录（时间 + 越级内容 + 用户原话），供事后追溯——已有功能目录 → 该功能的 `开发日志.md`；项目级阶段（尚无功能目录）→ `docs/开发记录/越级记录.md`（不存在则创建）。守卫是防跑偏的，不是和用户较劲的。

## 四、文档结构约定

```
specs/
├── CONSTITUTION.md            ← 本文件
├── TOOLCHAIN.md               ← 工具链配置（测试/lint/验收工具）
├── 产品概述.md / 技术栈.md / 项目结构.md / 开发规范.md / 开发路线图.md
├── features/{功能名}/
│   ├── 需求.md                ← 含 AC 列表
│   ├── 技术方案.md            ← 含 AC 覆盖总表
│   ├── 任务规划.md            ← 含验证标准与切片
│   ├── 开发日志.md             ← 时间序追加：阶段完成/变更/越级/review 摘要
│   └── reports/               ← 阶段完成报告（轻量模式不产上下文包与证据包）
└── changes/
    ├── {功能名}/
    │   └── CR-{编号}-{中文slug}/  ← 进行中变更（编号在本功能内自增，slug 用中文短语）
    │       ├── 变更提案.md    ← 变更原因 + 四层影响分析
    │       ├── 变更任务.md       ← 增量任务（含回归验证任务）
    │       └── 归并清单.md     ← 归并清单：正典哪些文档哪些节要改
    └── archive/{功能名}/      ← 已归档变更（{YYYYMMDD}-CR-{编号}-{中文slug}）
```

**命名约定**：产出文档用中文文件名（需求.md、技术方案.md、任务规划.md、开发日志.md、变更提案.md、变更任务.md、归并清单.md）；固定目录名（features/、changes/、archive/、reports/）与系统编号（CR-XXX、Task-XX、AC-XXX）用英文，目录名里的可变部分用中文——`{功能名}` 与 `specs/features/{功能名}/` 逐字同名，变更目录的 `{中文slug}` 取变更标题的中文短语（去标点虚词，≤20 字，如 `CR-001-单门店组织过滤`），**禁止自译成英文 kebab-case**；CONSTITUTION.md / TOOLCHAIN.md 两个全大写文件是工作流基础设施标记，保留英文名。AC、Task 与 CR 编号都只在**功能内**唯一（按功能目录分区，每个功能各自从 001 起）——不同功能撞号是正常的，同名编号靠功能名限定区分；跨功能引用他功能的 AC / 任务 / CR 时必须带功能名限定，写作 `评论功能#AC-003`、`评论功能#CR-003` 这样的形式，避免 grep 撞号。

**证据与日志文件命名**：如产生截图、日志等证据文件（**只本地留存，不入库**），同样用中文名：`Task-{XX}_{中文说明}.{扩展名}`——系统编号保留英文，说明用中文（允许 DDL / API / UI / Lint 等技术缩写），例如 `Task-03_测试日志.log`、`Task-03_DDL核查.md`、`Task-03_截图-01.png`。禁止 `task01_ddl_check.md` 这类无系统编号、英文短语拼出来的自创文件名。

**开发日志条目格式**（所有 Skill 统一遵守）：每条一行，追加到文件末尾——`- YYYY-MM-DD [阶段完成|变更|归档|审查|修复|越级] 一句话摘要`。

**审查条目固定格式**（归档门禁依赖它，不允许自由发挥）：

- 阶段级（当前格式）：`- YYYY-MM-DD [审查] 阶段{N} PASS|FAIL 一句话摘要`；变更任务用 `- YYYY-MM-DD [审查] CR-{编号} PASS|FAIL 一句话摘要`。
- 逐任务（仅旧项目兼容）：`- YYYY-MM-DD [审查] Task-{编号} PASS|FAIL 一句话摘要`。

feature-review 必须按当前阶段级格式写。**"待验证"按 FAIL 记录**——它的意思是"证据不足，等于未通过"，不允许写成 PASS。

**归档核对的兼容规则**（feature-evolution 执行）：阶段/CR PASS 覆盖该阶段全部任务；旧项目同一行同时出现 `Task-{编号}` 与 `PASS`，视为该任务审查通过——这条**只用于识别历史遗留写法**，凡是靠它放行的，归档报告里必须注明"按兼容规则通过"。本次归档过程中**新写入**的审查记录仍须严格符合上面的当前格式，不合规一律视为未通过。

**路径基准**：本文件与所有 Skill 正文中出现的 `specs/...`、`docs/...` 一律相对**用户项目根目录**；Skill 正文中的 `assets/...` 一律相对**该 Skill 自身目录**。两者不能混算——技能包被复制到 `~/.agents/skills/` 等位置后，`specs/` 并不在技能目录下。

**占位符约定**：模板里的 `{{...}}` 是必填占位，`[...]` 是示例或可选项提示——两者语义相同，都表示"这里必须替换成本项目的实际内容"。任何 Skill 生成文档后都要自检：**不得残留未替换的占位标记**；文档里只写了"示例"却没有任何项目具体信息，等同于没写。

**变更生命周期：** 分析（feature-evolution 生成变更文件夹）→ 执行（feature-implementation 执行 变更任务.md，阶段末过 feature-review）→ 归档（验收通过后按 归并清单.md 归并正典、追加变更日志、文件夹移入 `changes/archive/{功能名}/`）。

`specs/` 之外，项目根还有两个产物目录：`docs/开发记录/`（初始化记录）与 `docs/BUG修复文档/`（bug 修复报告）。

## 五、提交与推送约定

- **每阶段一个提交**：执行期不提交；阶段审查 PASS、收尾自检五项全过后，主会话提交一次，代码、测试、报告、验收记录一并纳入。单任务阶段同样只提交一次。
- **提交信息简短**：默认 `<type>(<scope>): <subject>`（项目开发规范另有规定时从其规定），subject 一行、不超过 50 字；body 最多一行 `Tasks: Task-XX ~ Task-YY`。禁止把变更文件清单、测试输出、diff 贴进 message。
- **审查在提交前**：阶段审查基于 `git diff <阶段起点>` + 各任务证据，不依赖逐任务 commit；审查 PASS 才允许提交。
- **不自动 push**：push 由用户决定；已推送的历史不改写，禁止 force push。
- **共享主干**：多人协作或受保护的 main，拉 `feat/...` 分支执行，阶段末在分支提交一次并 squash merge 回主干（仍是一个提交）；不在共享 main 上直接攒未提交改动。
- **证据清理**：原始日志/截图在阶段审查 PASS 后默认清理，证据目录只保留 `Task-{XX}_验收记录.md`（自包含）；需要视觉留档时转存仓库外。
- 非 git 项目按"无提交"处理：审查退到工作区 diff 或变更清单，并注明"未经 git 验证"。
